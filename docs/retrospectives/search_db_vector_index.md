# 검색이 5초나 걸린 이유 — 벡터 인덱스 누락 발견과 HNSW 적용

> 2026-06-10 발견, 2026-06-11 적용 | 분야: 검색 (DB 성능)

## 증상

서비스 응답이 체감상 느렸다. 모델 비교 평가를 진행하며 응답시간을 단계별(번역/검색/생성)로 분리 측정했더니, **검색 단계가 평균 4.8~5.7초**를 차지하고 있었다. 생성 모델을 아무리 빠른 것으로 바꿔도 검색에서 5초가 고정으로 나가는 구조였다.

## 추적

검색 시간은 두 단계의 합이다: ① 질문 임베딩 (Qwen3 서버 HTTP 호출) ② pgvector 벡터 검색.

각각 직접 측정했다.

| 단계 | 측정 시간 | 판정 |
|------|----------|------|
| 임베딩 (HTTP) | ~1.0s | CPU 서버 기준 정상 |
| DB 벡터 검색 쿼리 | 4~12s (콜드 캐시 12.2s) | **비정상** |

131만 건 테이블에서 벡터 검색이 이렇게 느릴 이유가 없어 인덱스를 확인했다.

```sql
SELECT indexname FROM pg_indexes WHERE tablename = 'laws';
-- 결과: laws_pkey (기본키 하나뿐)
```

**벡터 인덱스가 없었다.** 검색할 때마다 PostgreSQL이 1,313,837개 행 전부와 1024차원 L2 거리를 계산하는 풀스캔을 하고 있었다.

## 원인

pgvector는 인덱스 없이도 에러 없이 정확한 결과를 반환한다(풀스캔). 그래서:

- 개발 초기 데이터가 적을 때는 풀스캔도 빨라 문제를 느끼지 못했다.
- 데이터가 131만 건으로 늘며 서서히 느려져 "원래 RAG는 이 정도 걸리나?"로 인식됐다.
- 검색 5초가 LLM 생성 6~10초와 섞여 있어 병목이 드러나지 않았다.

## 해결 — HNSW 인덱스 적용

pgvector 0.6.0 환경에서 HNSW 인덱스를 생성했다. 서비스가 laws 테이블을 읽기만 하므로(일반 `CREATE INDEX`도 읽기는 허용) `CONCURRENTLY` 없이 빌드했다.

```sql
SET maintenance_work_mem = '2GB';
SET max_parallel_maintenance_workers = 4;

CREATE INDEX idx_laws_embedding_hnsw
ON laws USING hnsw (embedding vector_l2_ops);
```

- operator class는 쿼리가 실제 사용하는 연산자에 맞춰 `vector_l2_ops` (코드가 `l2_distance`/`<->` 사용). 임베딩이 L2 정규화되어 있어 L2 거리 순위는 코사인 유사도 순위와 수학적으로 동일하다.
- 애플리케이션 코드 변경 불필요 — 쿼리 플래너가 자동으로 인덱스를 사용

**빌드는 약 3시간 걸렸다.** 131만 × 1024차원 벡터 데이터만 ~5.4GB로 `maintenance_work_mem`(2GB)을 초과해, 그래프가 메모리에 다 들어가지 못하고 디스크를 오가며 빌드됐기 때문이다. 메모리가 충분했다면 수십 분 수준이었을 것이다.

## 결과

| 항목 | 적용 전 | 적용 후 |
|------|---------|---------|
| DB 벡터 검색 쿼리 (EXPLAIN ANALYZE) | 4~12s | **0.19s** |
| 검색 단계 평균 (임베딩 ~1s 포함) | 5.2s | **1.6s** |
| 평균 총 응답시간 (3.5-flash low 기준) | 11.5s | **8.0s** |

## 새로 드러난 트레이드오프 — 근사 검색의 재현율

속도와 함께 평가 지표를 재측정하자 검색 품질이 떨어져 있었다.

| 지표 | 풀스캔 | HNSW (ef_search=40 기본값) |
|------|--------|---------------------------|
| ContextRecall | 0.8917 | 0.825 |
| ContextPrecision | 0.8228 | 0.7589 |

HNSW는 근사(approximate) 검색이라 진짜 최근접 이웃을 일부 놓칠 수 있는데, pgvector의 탐색 폭 기본값(`hnsw.ef_search=40`)이 낮아 재현율 손실이 평가에 드러난 것이다. `ef_search`는 인덱스 재빌드 없이 조회 시 설정만 바꾸면 되므로 100으로 상향해 재측정하기로 했다.

```sql
ALTER DATABASE aidb SET hnsw.ef_search = 100;
```

## 배운 점

- **인덱스는 만들어야 생긴다.** pgvector는 인덱스 없이도 묵묵히 동작하므로 경고가 없다. 전용 벡터 DB라면 강제됐을 단계가 PostgreSQL 확장에서는 생략 가능해서 놓치기 쉽다.
- **단계별 측정 없이는 병목을 못 찾는다.** "전체가 느리다"는 정보로는 아무것도 고칠 수 없었고, 번역/검색/생성을 분리 측정하자 바로 드러났다.
- **근사 인덱스는 공짜가 아니다.** 속도를 얻는 대신 재현율을 내주는 트레이드오프이며, 도입 후 반드시 품질 지표를 재측정해야 한다. "빨라졌다"에서 멈췄으면 검색 품질 하락을 모른 채 배포했을 것이다.
- HNSW 빌드 시간은 `maintenance_work_mem`에 민감하다. 그래프가 메모리를 초과하면 수십 분이 수 시간이 된다.
