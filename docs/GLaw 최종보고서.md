# **1\. 프로젝트 개요**

## ---

**1.1 개발 배경**

세계화 흐름에 따라 어학연수, 해외 취업, 배낭여행 등으로 해외에 체류하는 대한민국 국민의 수가 급증하고 있습니다. 그러나 낯선 현지법과 언어 장벽, 높은 변호사 수임료 등의 이유로 예상치 못한 법적 분쟁(비자 거부, 임대차 계약 사기, 부당 해고 등) 발생 시 적절한 조치를 취하지 못하고 법적 고립 상태에 빠지는 경우가 많습니다.

최근 생성형 AI(LLM)의 발전으로 법률 자문 접근성이 높아졌으나, 일반적인 LLM 모델은 법률적 근거를 명확히 제시하지 못하고 거짓 정보를 정답처럼 출력하는 '환각 현상(Hallucination)'을 일으키는 한계가 있습니다. 따라서 신뢰성이 생명인 법률 분야에서는 확실한 현지 규정 원문을 기반으로 정답을 추출하는 시스템이 필수적입니다.

## **1.2 프로젝트 목표**

본 프로젝트는 RAG(Retrieval-Augmented Generation, 검색 증강 생성) 기술을 바탕으로 영미권 주요 국가의 최신 법령을 분석·구축하여, 해외 체류자들이 직면하는 법적 문제를 한국어로 명쾌하게 해결해 주는 '맞춤형 AI 법률 비서 플랫폼(GLaw)' 개발을 목표로 합니다.

# **2\. 요구사항 정의 및 핵심 기능**

## ---

**2.1 사용자 페르소나 정의**

* **해외 여행객:** 현지에서 교통사고, 물품 도난 등의 트러블이 발생했을 때 신속한 대처 법률 절차 확인 요구  
* **유학생/워킹홀리데이:** 현지 비자 연장 조건, 주당 합법 아르바이트 근무 시간, 임금 체불 발생 시 구제 절차 파악 요구  
* **장기 체류자 및 이주민:** 주택 임대차 계약서(Tenancy Agreement) 독소 조항 검토 및 현지 노무·세무 가이드라인 요구

## **2.2 시스템 핵심 기능**

* **AI 법률 Q\&A:** 사용자가 자연스러운 한국어로 질문하면, 시스템이 질문에 부합하는 현지 법령(영어)을 실시간 탐색 및 요약하여 정확한 한국어 답변을 표출합니다.  
* **국가 간 법률 비교 분석:** 한국의 법제도와 현지 국가의 법제도를 1:1로 매칭하여 명확한 텍스트 결과값으로 차이점을 비교해 줍니다.  
* **체류 조건별 리스크 알림:** 비자 종류, 체류 기간 등 사용자 정보를 바탕으로 위반하기 쉬운 현지 규제나 리스크 요소를 사전에 스크리닝하여 결과값으로 출력합니다.

대용량 벡터 데이터의 실시간 검색 성능을 확보하기 위해 관계형 데이터베이스인 PostgreSQL에 pgvector 익스텐션을 결합하였으며, HNSW(Hierarchical Navigable Small World) 인덱스 트리를 구성하여 밀리초(ms) 단위의 고속 시맨틱 검색 환경을 구축하였습니다.

# **4\. AI 구조 설계 및 RAG 파이프라인**

## ---

**4.1 RAG 파이프라인 개요**

G.Law의 AI 답변 생성 파이프라인은 사용자의 한국어 질문이 입력된 시점부터 최종 답변이 반환되기까지 총 7단계를 순차적으로 거친다. 각 단계는 검색 정확도와 답변의 근거 충실도를 높이기 위해 독립적으로 설계되었으며, 핵심 구현은 `src/services/chat_service.py`의 `generate_answer()` 함수에 집약되어 있다.

**4.2 7단계 파이프라인 상세**

**① 질문 재구성 (Contextualize)**
대화형 세션(`session_id`)이 존재하는 경우, 이전 대화 맥락을 참조하여 후속 질문을 독립적으로 이해 가능한 형태로 재구성한다. 예를 들어 "그러면 벌금은 얼마야?"라는 후속 질문은 "캘리포니아 음주운전 벌금은 얼마인가?"와 같이 맥락이 포함된 질문으로 변환된다. 이는 벡터 검색 시 대화 맥락 없이도 올바른 법령을 검색할 수 있도록 하기 위함이다.

**② 번역 (Translation)**
재구성된 질문을 Cloud Translation LLM(`general/translation-llm`)을 통해 한국어에서 영어로 번역한다. 번역된 영어 질문은 벡터 검색에만 사용되며, 이후 답변 생성 단계에는 원본 한국어 질문이 그대로 전달된다. 이를 통해 생성 모델이 자연스러운 한국어로 답변하도록 유도한다. 번역 모듈을 생성 모델로부터 분리함으로써 번역 처리 시간을 기존 2~7초에서 평균 약 0.5초 수준으로 단축하였다.

**③ 질문 재작성 (Query Rewrite)**
번역된 영어 질문을 벡터 검색에 최적화된 형태로 재작성한다(`RAG_ENABLE_REWRITE=True`). 막연하거나 구어체로 작성된 질문을 법령 조항이 실제로 서술하는 방식의 표현으로 보강함으로써 검색 재현율을 높인다.

**④ 임베딩 (Embedding)**
재작성된 영어 질문을 자체 호스팅 중인 Qwen3-Embedding-0.6B 모델 서버(`embedding_server/embed_server.py`)로 전송하여 1024차원 벡터로 변환한다. 쿼리 임베딩 시에는 Qwen3 공식 가이드에 따라 `"Instruct: {task}\nQuery: {query}"` 형식의 접두사를 적용하는 비대칭(Asymmetric) 방식을 사용하며, Last-Token Pooling과 L2 정규화를 적용한다. 데이터베이스에 저장된 법령 문서 벡터와 동일한 방법으로 정규화되어 있어 L2 거리 순위와 코사인 유사도 순위가 일치한다.

**⑤ 벡터 검색 (Vector Search)**
변환된 쿼리 벡터를 PostgreSQL + pgvector를 통해 DB에서 검색한다. 인덱스는 HNSW(`hnsw (embedding vector_l2_ops)`, `ef_search=100`)를 사용하며, 상위 7개(`top_k=7`) 조항을 L2 거리 기준으로 추출한다. HNSW 인덱스 도입으로 풀스캔 대비 검색 처리 시간이 5.28초에서 1.36초로 단축되었다.

**⑥ 임계값 필터 — 가드레일 ①**
검색된 조항들의 L2 거리가 임계값(0.95)을 초과하는 경우 관련성이 없는 것으로 판단하여 제외한다. 필터링 후 남은 조항이 0건이면 LLM을 호출하지 않고 즉시 "관련 정보를 찾을 수 없습니다" 응답을 반환한다. 이를 통해 무관한 법령 조항을 근거로 잘못된 답변이 생성되는 것을 사전에 차단한다.

**⑦ 답변 생성 — 가드레일 ②**
임계값을 통과한 법령 조항들을 컨텍스트로 삼아 Gemini 3.1 Flash Lite 모델이 한국어 답변을 생성한다(`src/prompts/chat.yaml`). 프롬프트에는 "답변은 반드시 아래 제공된 법률 조항만을 근거로 작성하십시오. 제공된 조항에 없는 내용은 절대 지어내지 마십시오."라는 제약이 명시되어 있으며, 답변에는 핵심 요약, 법적 근거, 주의사항, 참고 법령 조항 번호가 구조화된 형식으로 포함된다.

**4.3 핵심 기술 선정 근거**

**임베딩 모델 — Qwen3-Embedding-0.6B 자체 호스팅**
임베딩 모델 선정 시 MTEB(Massive Text Embedding Benchmark)의 법률 문서 검색(Legal Retrieval) 태스크 기준으로 모델을 비교하였다. 평가 지표는 검색 랭킹 품질을 측정하는 NDCG@10(Normalized Discounted Cumulative Gain)을 사용하였으며, Qwen3-Embedding-0.6B는 0.8677을 기록하여 232개 후보 모델 중 상위권에 위치한 반면, 범용 임베딩 API인 Google `text-embedding-005`는 0.4464로 약 2배의 성능 차이를 보였다. 정확도 우위와 법령 데이터 외부 전송을 방지하기 위한 데이터 보안 이유로 자체 호스팅 방식을 채택하였다.

**생성 모델 — Gemini 3.1 Flash Lite**
생성 모델은 3-flash, 3.1-pro, 3.5-flash, 3.1-flash-lite 4개 후보를 RAGAS 프레임워크로 평가하여 선정하였다. 법률 서비스의 특성상 답변이 검색된 법령 조항을 얼마나 충실히 따르는지를 나타내는 Faithfulness(근거충실도)를 가장 중요한 지표로 삼았다. Gemini 3.1 Flash Lite는 후보 모델 중 Faithfulness가 가장 높았고, 응답 속도도 약 4.7초로 비교 대상(9.0초)의 절반 수준이었다. 또한 RAG 환경에서 과도한 추론(Thinking)이 컨텍스트 이탈을 유발할 수 있어 추론 기능을 비활성화한 상태로 운용하고 있다.

**번역 모델 — Cloud Translation LLM 분리**
초기 설계에서는 생성 모델이 번역까지 담당하였으나, 번역 단계를 Cloud Translation LLM(`general/translation-llm`)으로 분리하였다. 이를 통해 번역 처리 시간이 2~7초에서 약 0.5초로 약 76% 단축되었다. 또한 번역 모듈이 고정됨에 따라 검색 성능 지표(Context Recall, Context Precision)가 생성 모델 교체의 영향을 받지 않게 되어, 이후 생성 모델 비교 실험의 통제 변수가 명확해지는 부수 효과도 얻었다.

# **5\. 시스템 아키텍처 및 백엔드 설계**

## ---

**5.1 클라우드 인프라 및 네트워크 환경**

G.Law는 안정적인 서비스 운영과 배포 자동화를 고려하여 Google Cloud Platform(GCP) 기반의 클라우드 인프라를 구성하였습니다. 전체 운영 환경은 GCP 내부의 VPC 네트워크를 중심으로 설계하였으며, 외부 사용자의 요청이 DNS, CDN, 로드 밸런서를 거쳐 애플리케이션 서버로 전달되는 구조로 구성하였습니다.

정적 리소스는 Cloud Storage와 Cloud CDN을 활용하여 제공하고, 사용자의 요청은 로드 밸런서를 통해 Spring Boot 기반 백엔드 서버로 전달됩니다. 백엔드 서버는 사용자 인증, 온보딩, 법률 모아보기, 북마크, 마이페이지 등 서비스 운영에 필요한 주요 기능을 처리합니다. 데이터베이스는 PostgreSQL을 사용하여 사용자 정보, 관심 국가, 법률 정보, 북마크 정보, 비교 조합, 저장된 리스크 정보 등을 관리합니다.

또한 인프라 관리를 효율화하기 위해 Terraform을 활용하여 클라우드 리소스를 코드 기반으로 관리할 수 있도록 구성하였습니다. 개발자가 GitHub에 코드를 반영하면 GitHub Actions를 통해 빌드 및 배포 과정이 수행되며, Docker 이미지는 Docker Hub를 통해 관리됩니다. 이를 통해 수동 배포 과정에서 발생할 수 있는 오류를 줄이고, 일관된 배포 환경을 유지할 수 있도록 하였습니다.

네트워크 측면에서는 VPC 내부에 Public 영역과 Private 영역을 구분하여 구성하였습니다. 외부 요청을 받아야 하는 로드 밸런서와 보안 연결 요소는 Public 영역에 배치하고, 애플리케이션 실행 환경과 데이터베이스는 상대적으로 보호된 영역에서 관리되도록 설계하였습니다. 또한 SSL/TLS를 적용하여 사용자 요청이 안전하게 전달될 수 있도록 하였으며, 필요한 외부 통신은 NAT 구성을 통해 통제할 수 있도록 하였습니다.

## **5.2 전체 시스템 구조**

G.Law의 시스템은 크게 프론트엔드, Spring Boot 백엔드, 데이터베이스, AI 기능 영역으로 구성됩니다. 프론트엔드는 사용자가 로그인, 국가 선택, 법률 조회, 자연어 질문 등의 기능을 사용할 수 있는 화면을 제공합니다. Spring Boot 백엔드는 사용자 요청을 처리하고, 데이터베이스와 연동하여 서비스 운영에 필요한 데이터를 저장하고 조회합니다.

AI 기능 영역은 법률 Q\&A 챗봇, 국가 간 법률 비교, 리스크 관리 기능을 담당합니다. 이번 프로젝트에서는 백엔드가 사용자 관리와 법률 데이터 관리 기능을 중심으로 동작하고, AI는 법률 정보 분석과 답변 생성 기능을 담당하도록 역할을 분리하였습니다. 이를 통해 백엔드와 AI의 책임 범위를 명확히 구분하고, 각 기능을 독립적으로 개발할 수 있도록 구성하였습니다.

## **5.3 Spring Boot 백엔드 설계**

Spring Boot 백엔드는 G.Law의 주요 서비스 로직을 담당합니다. 사용자 인증 기능으로는 구글 로그인을 기반으로 한 소셜 로그인, 로그아웃, 회원 탈퇴, 토큰 재발급 기능을 제공합니다. 로그인 이후 사용자는 온보딩 과정을 통해 관심 국가를 설정할 수 있으며, 해당 정보는 이후 법률 조회와 마이페이지 개인화 기능에 활용됩니다.

백엔드의 핵심 기능 중 하나는 법률 모아보기 기능입니다. 사용자는 국가, 분야, 키워드를 기준으로 법률 정보를 조회할 수 있으며, 법률 목록은 페이징 처리를 통해 제공됩니다. 특정 법률을 선택하면 상세 페이지에서 법령명, 조항 번호, 조항 본문, 출처 URL 등의 정보를 확인할 수 있습니다. 또한 사용자는 필요한 법률을 북마크로 저장하거나 저장을 해제할 수 있으며, 저장된 법률은 마이페이지에서 다시 확인할 수 있습니다.

마이페이지에서는 사용자의 관심 국가 조회 및 수정, 북마크한 법률 조회, 저장한 국가 간 법률 비교 조합 조회, 저장한 리스크 정보 조회 기능을 제공하도록 설계하였습니다. 이를 통해 사용자는 자신에게 필요한 국가별 법률 정보를 지속적으로 관리할 수 있습니다.

## **5.4 AI 기능 설계 (유호찬)**

FastAPI 기반 AI 서버(`/api/ai`)는 Spring Boot 백엔드로부터 요청을 받아 처리하며, 법률 Q&A, 국가 간 법률 비교, 리스크 카드 조회의 세 가지 기능을 제공한다.

**법률 Q&A (`POST /api/qna`)**
사용자의 자연어 질문과 대상 국가(`country_id`), 세션 식별자(`session_id`)를 입력받아 4번에서 기술한 7단계 RAG 파이프라인을 실행한 뒤 한국어 답변, 근거로 사용된 법령 ID 목록(`related_law_id_list`), 검색 성공 여부(`search_success`)를 반환한다. `session_id`가 존재하는 경우 이전 대화 맥락을 활용하여 후속 질문도 정확하게 처리한다. Spring Boot는 반환된 `related_law_id_list`를 사용하여 법령 상세 페이지로의 링크를 사용자에게 제공할 수 있다.

**국가 간 법률 비교 (`POST /api/compare`)**
비교 주제(`query`)와 두 국가 코드(`country_id_1`, `country_id_2`)를 입력받아 각 국가에 대해 독립적으로 벡터 검색과 답변 생성을 수행한 뒤, 두 국가의 요약과 공통점·차이점을 구조화하여 반환한다. 비교 결과 전문을 DB에 저장하는 대신 비교 주제와 국가 조합만 Spring Boot에서 관리하며, 사용자가 다시 접근할 때 해당 조합으로 비교를 재실행하는 방식으로 중복 데이터 저장을 최소화하였다.

**리스크 카드 (`POST /api/risk`)**
국가(`country_id`), 체류 목적(`travel_purpose`), 비자 종류(`visa_type`), 연령대(`age_band`)를 입력받아 해당 조합에 맞는 리스크 카드를 반환한다. 리스크 카드는 실시간 생성 방식이 아닌 사전 생성(Pre-generation) 방식으로 운영된다. 가능한 입력 조합 약 1,000가지에 대해 미리 약 4,920장의 카드를 생성하여 `data/risk_cards.json`에 저장해두었으며, 사용자 요청 시 해당 조합의 카드를 즉시 조회하여 반환한다. 사전 생성된 카드는 `src/scripts/data_risk_review_cards.py`를 통해 인용된 법령 원문과 자동 대조하는 팩트체크 과정을 거쳤다. 팩트체크는 처벌 주체 오인, 근거 없는 수치, 확대 해석, 한국법 속인주의 오적용 여부를 판정하며, 오류가 발견된 카드는 자동으로 교정된다.

## **5.5 데이터베이스 설계**

G.Law의 데이터베이스는 사용자 데이터와 법률 데이터를 중심으로 설계하였습니다. 사용자 관련 데이터에는 회원 정보, 관심 국가, 북마크한 법률, 저장한 비교 조합, 저장한 리스크 정보가 포함됩니다. 법률 데이터에는 국가 코드, 법령명, 법률 분야, 조항 번호, 조항 본문, 원문 출처 URL, 마지막 업데이트 날짜 등이 포함됩니다.

법률 모아보기 기능에서는 백엔드가 데이터베이스에 저장된 법률 목록과 상세 조항을 조회합니다. 사용자는 국가와 분야를 기준으로 법률을 탐색하거나, 키워드 검색을 통해 필요한 법률을 찾을 수 있습니다. 북마크 기능은 사용자가 특정 법률 조항을 저장하는 방식으로 설계하여, Q\&A 답변 저장과 법률 저장 로직을 분리하지 않고 하나의 저장 구조로 단순화하였습니다.

AI 기능에서 활용할 법률 데이터는 국가별, 주제별, 조항별로 정리될 수 있도록 설계하였습니다. 각 법률 조항에는 원문 출처 URL을 포함하여 답변의 근거를 확인할 수 있도록 하며, 향후 RAG 기반 법률 답변 생성에 활용될 수 있는 구조를 고려하였습니다.

# **6\. 출력 형태 및 결과 검증 전략 (유호찬)**

## ---

**6.1 Q&A 답변 출력 형식**

법률 Q&A 답변은 일반 사용자가 복잡한 법률 조항을 빠르게 파악할 수 있도록 구조화된 형식으로 출력된다(`src/prompts/chat.yaml`). 답변 가능한 경우 아래 4개 섹션으로 구성된다.

* **핵심 요약:** 질문에 대한 결론(합법/불법 여부, 조건별 구분)을 1~2문장으로 명확하게 제시한다.
* **법적 근거 및 상세 내용:** 처벌 수위, 적용 요건 등을 불릿 형식으로 간결하게 작성한다. 본문에는 조항 번호를 직접 노출하지 않고, "초범의 경우", "혈중알코올농도 0.08% 이상인 경우"와 같이 자연어로 서술하여 가독성을 높인다.
* **주의사항 및 예외:** 가중 처벌, 예외 조건 등 추가로 주의해야 할 사항이 있는 경우에만 포함한다. 마약류·도박·성범죄·총기·세관 분야에서는 한국 법률의 속인주의 적용 여부를 일반 상식 수준에서 안내한다.
* **참고 법령:** 답변 근거로 사용된 법령 조항 번호를 나열한다. Spring Boot는 이 목록을 활용하여 사용자가 해당 법령 원문 상세 페이지로 이동할 수 있는 링크를 제공한다.

답변할 수 없는 경우(검색 결과 0건 또는 관련성 없음)에는 "죄송합니다. 제공된 정보만으로는 답변하기 어렵습니다."만을 반환하며, 임의로 내용을 생성하지 않는다.

**6.2 이중 가드레일 검증 전략**

G.Law의 Hallucination 방지 전략은 파이프라인 내 두 지점에서 독립적으로 작동한다.

**가드레일 ①: 임계값 필터 (검색 단계)**
벡터 검색 후 L2 거리가 임계값(0.95)을 초과하는 조항은 관련성이 없는 것으로 판단하여 제거한다. 필터링 후 잔여 조항이 0건이면 LLM을 호출하지 않고 즉시 "정보 없음" 응답을 반환한다. 이를 통해 질문과 무관한 법령을 근거로 잘못된 답변이 생성되는 것을 사전에 차단한다.

**가드레일 ②: 프롬프트 제약 (생성 단계)**
LLM 프롬프트에 "답변은 반드시 아래 제공된 법률 조항만을 근거로 작성하십시오. 제공된 조항에 없는 내용은 절대 지어내지 마십시오."라는 명시적 제약을 포함한다. 모델은 검색된 법령 조항의 범위 내에서만 답변을 구성하며, 답변 말미에 면책 고지("본 답변은 법률적 조언이 아니며 정보 제공을 목적으로 합니다. 구체적인 법적 판단은 반드시 전문 변호사와 상담하시기 바랍니다.")를 포함한다.

**6.3 리스크 카드 자동 팩트체크**

리스크 카드는 사전 생성 후 `src/scripts/data_risk_review_cards.py`를 통해 자동 팩트체크를 실시한다. 검수 모델은 각 카드의 내용을 인용된 법령 원문과 대조하여 아래 4가지 오류 유형을 판정하고, 오류가 발견되면 자동 교정한다.

* 처벌 주체 오인 (예: 고용주 책임을 근로자 책임으로 서술)
* 근거 없는 수치 (법령에 명시되지 않은 벌금액, 징역 기간)
* 확대 해석 (법령이 규정한 것보다 넓은 범위로 서술)
* 한국 법률 속인주의 오적용 (마약·도박·성범죄·총기·세관 이외 분야에 한국법 언급)

동일 내용의 카드는 캐시를 통해 LLM 호출을 재사용하여 검수 비용을 절감하며, 검수가 완료된 카드는 `_review` 필드로 표시하여 중단 후 재실행 시 이어서 진행할 수 있다.

# **7\. 성능 지표 및 기대 효과 (유호찬)**

## ---

**7.1 RAG 파이프라인 성능 평가**

G.Law의 AI 성능은 RAGAS(RAG Assessment) 프레임워크를 사용하여 평가하였다. 평가 데이터셋은 실제 서비스 사용자의 표현 방식을 반영한 30개 문항 수동 제작 세트(`ragas_testset_casual.csv`)를 최종 기준으로 사용하였으며, 채점 모델은 `gemini-3-flash-preview`(추론 비활성화)로 전 실험에서 동일하게 고정하였다.

평가 지표는 4가지를 사용하였다. **Context Recall**은 정답 도출에 필요한 법령 조항이 검색 결과에 얼마나 포함되었는지를 나타내며, 누락 없이 관련 법령을 찾는 능력을 측정한다. **Context Precision**은 검색된 조항 중 실제로 답변에 기여한 비율을 나타낸다. **Faithfulness(근거충실도)**는 생성된 답변의 각 주장이 검색된 법령 조항에 의해 뒷받침되는 비율을 측정한다. **FactualCorrectness(사실정확도)**는 답변의 원자적 주장(Atomic Claim)들이 참조 답변의 주장과 얼마나 겹치는지를 F1 점수로 표현한다.

비교 기준은 RAG를 사용하지 않고 동일한 생성 모델(Gemini 3.1 Flash Lite)로 직접 질문에 답변하게 한 "RAG 미적용" 설정이다.

| 지표 | RAG 미적용 | G.Law (RAG 적용) |
|---|---|---|
| FactualCorrectness | 0.1573 | **0.3433** |
| Faithfulness | 측정 불가 | **0.8057** |
| Context Recall | 측정 불가 | **0.8222** |
| Context Precision | 측정 불가 | 0.8163 |

RAG 도입으로 FactualCorrectness는 0.16에서 0.34로 약 2.2배 향상되었다. Faithfulness 0.81은 생성된 답변의 81%에 해당하는 주장이 검색된 법령 조항으로 근거를 확인할 수 있음을 의미하며, Context Recall 0.82는 정답 도출에 필요한 법령의 82%가 검색 단계에서 실제로 포함되었음을 나타낸다. Faithfulness와 Context Recall은 검색 결과 없이는 정의되지 않아 RAG 미적용 설정에서는 측정이 불가능하다.

**7.2 시스템 처리 성능**

RAG 파이프라인의 각 단계에 대한 처리 시간도 측정하였다.

| 항목 | 개선 전 | 개선 후 |
|---|---|---|
| 검색 단계 평균 (임베딩 + DB 쿼리) | 5.28초 (풀스캔) | 1.36초 (HNSW ef=100) |
| 번역 처리 시간 | 2~7초 | 약 0.5초 |

검색 속도 개선은 PostgreSQL + pgvector에 HNSW 인덱스를 적용한 결과이며, 약 131만 건의 법령 벡터를 대상으로 한 풀스캔 방식과 비교하여 처리 시간이 약 74% 단축되었다. 번역 속도 개선은 번역 모듈을 생성 모델에서 Cloud Translation LLM으로 분리한 결과로, 약 76% 단축되었다.

임베딩 모델 선정 단계에서는 MTEB 법률 검색 태스크 기준 NDCG@10을 비교하였다. Qwen3-Embedding-0.6B는 0.8677을 기록하여 범용 API인 Google `text-embedding-005`(0.4464) 대비 약 2배의 검색 랭킹 품질을 보였다.

**7.3 향후 과제**

검색 성능을 더 높이기 위한 Cross-Encoder 기반 Reranking 적용, 대용량 법령 데이터의 정기 업데이트를 위한 스케줄러 파이프라인 구축, 서비스 국가 확장(일본, 베트남, EU 등)이 향후 과제로 남아 있다.
